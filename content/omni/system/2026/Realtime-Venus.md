# Realtime-Venus: A full-duplex interaction system with asynchronous delegation

论文链接：https://arxiv.org/pdf/2609.13814

代码链接：https://github.com/inclusionAI/Realtime-Venus

## 摘要

在数字和物理环境中实现自然交互，需要持续的感知能力和及时的响应。口语对话依赖于声学和语言线索，而视频交互则要求将对话建立在不断变化的视觉情境之上。我们提出了 **Realtime-Venus**，这是一个主动式全双工交互系统，包含两个独立训练的 9B 模型：用于视听交互的 **Realtime-Venus-Omni** 和用于口语交互的 **Realtime-Venus-Audio**。每个模型都作为一个完整的对话前端，通过统一的因果时间轴（涵盖用户输入、模型输出及任务委派事件），集成了持续感知、对话控制和原生语音生成功能。系统采用双循环运行时架构，协调实时交互与后台推理及工具执行。在 **Realtime-Venus-Harness** 异步执行任务并返回结果以融入当前对话的同时，前台交互依然能够持续进行。这两个模型遵循一套统一的后训练方案，该方案结合了离线理解、主动式全双工交互轨迹以及任务委派工作流。在参与评估的在线模型中，Realtime-Venus-Omni 在八项视频基准测试中的六项（包括 StreamingBench 70.2%、OVO-Bench 64.7% 和 Daily-Omni 81.3%）中取得了最高分。在八项音频理解与口语问答基准测试中，Realtime-Venus-Audio 在 MMAU (78.0%)、MMAU-Pro (63.2%)、Llama Questions (83.8%) 和 Speech-CMMLU (67.8%) 等测试中均领先于其他对比模型，并在 VoiceBench AlpacaEval 中达到了 4.81 分（与该项测试中的最佳表现持平）。在 Full-Duplex-Bench v1.5 基准测试中，Realtime-Venus-Audio 能够响应 75% 的用户打断；在面对“反馈信号”（backchannels）、“针对他人的语音”以及“背景语音”时，其对话延续率分别达到了 97%、88% 和 86%，在所有三项延续性指标上均优于 Gemini 3.1 Live 和 GPT-4o。

自然交互要求系统能够解读持续获取的观测信息，并决定何时以及如何做出响应——这包括在用户未明确提出请求时，主动发起响应。近期的模型正日益将感知、语音生成和对话控制功能整合在一起。Moshi 支持并发语音建模；Qwen2.5-Omni 和 Qwen3-Omni 将多模态感知与原生流式语音生成相结合；而 MiniCPM-o 4.5 则进一步将这些能力扩展至主动式全双工视频交互。针对语音智能体的研究，也在探索对话过程中的信息检索、工具调用以及异步外部计算等功能。

在同一会话中，持续交互与外部计算在不同的时间尺度上运行。后台任务需要对请求及其支撑依据进行稳定记录，但其结果必须在对话上下文中进行解读——而这一上下文在任务执行期间可能已经发生了变化。协调“任务捕获”与“对话结果呈现”之间的关系，对于维持交互的一致性至关重要。

我们推出了 **Realtime-Venus**，这是一个主动式全双工交互系统，结合了原生对话建模与异步任务委派机制。该系统基于 MiniCPM-o 4.5 构建，包含两个独立训练的模型：用于视听交互的 **Realtime-Venus-Omni** 和用于语音交互的 **Realtime-Venus-Audio**。每个模型均可作为完整的对话前端，具备持续感知、对话控制及原生语音生成能力。系统采用统一的流式架构，将用户观测信息、模型输出、内部委派请求以及后台处理结果整合在同一因果时间轴上。在此架构下，前端模型能够协同预测交互控制 tokens、回复文本及委派请求。该统一策略支持在用户进行“回馈性应答”（backchannels，如“嗯”、“哦”等）时维持当前的回复状态；在用户提出修正后，动态调整后续尚未表达的内容；并在任务需要外部能力支持时，自动触发后台处理流程。

我们将这些模型与 **Realtime-Venus-Harness** 相结合——这是一个用于异步执行功能任务并交付结果的共享框架。在双循环运行时架构中，前端负责维持实时交互，而 Realtime-Venus-Harness 则在后台管理被委托的任务。**每一项委托请求都与其发起的会话绑定，并附带一份请求发起时可用证据的快照**。该框架将任务分发给已注册的功能模块进行异步执行，并将符合条件的结果作为私有上下文返回。系统会通过“时效性检查”来确定结果是否有效，并利用“**回放感知交付**”机制来控制结果何时重新融入对话流程。随后，前端会结合当前的对话上下文对返回的信息进行解读，并据此生成面向用户的响应。这种设计既确保了后台执行时上下文的稳定性，又允许前端根据用户意图的后续变化灵活调整响应内容。

训练过程需要一系列轨迹，将对话事件、交互决策以及委托执行关联起来。我们开发了一套统一的数据流水线，整合了场景规划、语音生成和时间对齐功能。（1）在 **duplex 场景**中，系统能够区分“回馈信号”（backchannels）或针对他人的话语，与那些需要停止、修正或重定向响应的“打断”行为。（2）在**主动式交互**轨迹中，系统可判断何时发起响应，以及何时继续倾听。（3）在**委托场景**中，系统将特定请求与后台执行、信息反馈及后续响应关联起来。该流水线在统一的时间轴上，将上述各类行为整合进对话流程之中。

由此得出的轨迹支持一种通用的后训练处理方案，该方案融合了离线理解、主动式全双工交互以及任务委派流程。*Realtime-Venus-Omni* 同时利用视听数据和纯音频数据，而 *Realtime-Venus-Audio* 则仅使用纯音频数据子集。监督过程涵盖了交互控制的转换及其后续生成环节，将“何时倾听、何时发言或何时委派”的决策与随后的响应关联起来。

相关评估涵盖了理解能力、对话连贯性以及任务委派能力。在八项视频基准测试中，Realtime-VenusOmni 在其中六项的表现优于其他参评的在线模型；而 Realtime-VenusAudio 则在多项音频理解及语音问答对比测试中取得了最高分。全双工评估结果显示，在无干扰对话场景下，该模型保持了极高的对话连贯率。此外，针对工具使用与任务委派决策的专项评估，不仅区分了“正确的任务分发”与“成功的任务完成”，还揭示了在对话过程中执行外部任务所面临的挑战。

我们的贡献总结如下：
- **Proactive full-duplex interaction models**。我们开发了 Realtime-Venus-Omni 和 RealtimeVenus-Audio，这是两个分别训练的 9B 模型，分别用于主动式视听交互和全双工语音对话。这两个模型在统一的流式处理框架下，集成了持续感知、对话控制、原生语音生成以及私有任务代理功能。据我们所知，Realtime-Venus-Omni 是首个支持全双工交互的 omni 模型；它能够在维持视频交互的同时，异步调用后端进行推理和工具执行。此外，通过内存增强技术，该模型还支持长达数小时的视频理解能力。
- **Asynchronous capability execution with Realtime-Venus-Harness**。我们引入了一种共享执行框架，该框架将任务与请求边界处可用的证据相关联，异步执行已注册的功能，并将结果返回至发起请求的会话，同时确保前端能够掌控对话响应。
-  **A coupled duplex and delegation data pipeline**。我们开发了一套流程，结合了情境规划、话语实现和时间对齐，旨在构建出将对话事件与委托请求、背景结果及后续回应相串联的轨迹。

## 2.Related Work

**Omni-modal understanding**。Omni 模型在统一架构内整合了文本、视觉和音频，以实现理解与响应生成。Gemini 通过学习交错的多模态数据，具备了跨模态理解与推理能力；而 GPT-4o 则通过涵盖文本、视觉和音频的端到端训练，支持原生语音交互。开源模型进一步扩展了这些能力：Baichuan-Omni-1.5 结合了多模态理解与端到端语音生成；MiniCPM-o 2.6 则通过在线模态处理和时分复用技术，支持连续的视听输入及流式语音输出。Qwen2.5-Omni 引入了时间对齐的视听表征以及“思考者-说话者”（Thinker–Talker）架构；Qwen3-Omni 在此基础上进一步演进，融入了混合专家（MoE）组件和多码本（multi-codebook）语音生成技术。这些进展实现了对多种模态的覆盖及流式输出；而全双工交互则要求输入的信息能够实时影响正在进行的响应过程。

**Audio understanding and speech generation**。音频-语言模型采用多种互补方法，将声学表征与语言模型相连接。SALMONN 通过“窗口级 Q-Former”（window-level Q-Former）将语音和通用音频编码器与大语言模型（LLM）相连。Qwen-Audio 通过带有层级任务标签的多任务预训练，统一了多种音频理解任务；而 Qwen2-Audio 则利用自然语言提示，支持语音指令及基于文本引导的音频分析。SpeechGPT 在实现“音频到文本”理解的基础上，通过模态适配和跨模态指令微调，将离散语音表征融入大语言模型，从而具备了语音生成能力。近期的一些模型进一步优化了这种融合方式：Kimi-Audio 将连续声学特征与离散语义 token 相结合；MiMo-Audio 则采用基于分块（patch-based）的音频编解码机制，并结合预测下一个 token 的预训练方法。Fun-Audio-Chat 结合了双分辨率语音表征、分阶段后训练以及模型融合技术；Step-Audio 2 则引入了文本与音频的交错生成、面向推理的强化学习以及外部检索机制。我们的音频前端旨在保留声学与语义处理能力的同时，协同学习对话控制与任务委派。

**Proactive and full-duplex interaction**。全双工（Full-duplex）模型通过在生成回复的同时处理输入的语音，来解决对话时序问题。Moshi 将用户和助手的音频建模为并行流，并通过其“内心独白”（Inner Monologue）机制将文本与语音关联起来。Freeze-Omni 在大语言模型（LLM）的隐状态上引入了一个辅助分类器，该分类器通过联合状态预测和语言建模目标进行训练，旨在预测分段级别的对话状态，并判断输入的语音是否需要打断当前的回复生成。FunAudio-Chat 扩展了联合语音-文本建模，采用了并行输入流和合成的并发对话。JoyAI-Talker 结合了模块化的“思考者-说话者”（Thinker–Talker）架构与 Joy-Duplex 技术，用于交互状态预测和对话轮次控制。在多模态场景下，MiniCPM-o 4.5 引入了 Omni-Flow 机制，将输入的音视频流与输出进行对齐，从而实现同步感知、语音交互和主动参与。针对视频模态的方法则探讨了何时应基于观察结果做出响应：LiveStar 结合了“回复-静默”解码与具备记忆感知能力的流式推理；而 MMDuet2 则通过多轮强化学习来学习回复的时机与内容。我们的方案扩展了原生的流式交互模式，将对话控制、回复生成以及私有委托任务统一纳入到一个共享的策略框架与时间轴之中。

**Tool use and asynchronous delegation**。工具增强型语言模型将推理能力与外部功能相结合。ReAct 框架通过环境反馈，将推理过程与具体行动交织在一起。语音系统及多模态系统将这一思路扩展至持续交互场景中。DuplexSLA 联合建模语音与结构化行动通道，用于实现任务规划、交互控制及工具调用。MoshiRAG 为全双工语音模型提供了选择性的异步检索机制；DuplexOmni 则将连续的多模态交互与可插拔的异步“思考层”相结合。JoyAI-VL-Interaction 利用外部自动语音识别（ASR）和语音合成（TTS）组件，将主动式视觉交互与后台任务委托关联起来。GPT-Realtime 支持异步函数调用，而 NemotronLabs VoiceChat 则为工具调用脚本提供了独立的输出通道。我们研究了一种针对音频前端和全模态（omni）前端（两者均为独立训练）的私有委托接口。Realtime-Venus-Harness 通过在请求边界处固定证据、执行已注册的功能，并将结果返回至发起会话（以便整合进当前对话中），从而明确了执行边界。

**Interaction loop**。前端持续处理传入的媒体信息，更新会话状态，并控制何时进行监听、发言或让出话语权。它能够处理那些可直接回答的请求，并通过其原生的“思考者-发言者”（Thinker–Talker）架构，提供流式文本及语音输出。在发言或执行后台任务期间，感知功能始终保持活跃状态​​。

**Capability loop**。来自前端的私有自然语言委托请求会触发这一循环。宿主系统会将该请求区间从面向用户的输出中隐藏，捕获请求边界处的可用上下文，并创建一个异步工作项。harness 会选择相应的后端能力来完成任务，并将结果润色为适合口头表达的回复。符合条件的回复会通过私有的后台通道返回至原始会话。在持续的交互过程中，前端负责决定何时播报这些准备好的文本，而 harness 则负责确定其具体内容与措辞。

交互循环持续运行且对延迟敏感，而能力循环则按需处理任务，其执行时长可能更长。两者通过共享接口进行交互：输入端为受请求因果上下文约束的任务包，输出端为关联至原始会话的预备回复。这种机制支持在实时交互的同时进行异步执行，如图 4 所示。

### 3.2 Unified runtime abstraction

两种前端遵循相同的运行时结构：它们接收媒体信息及新返回的回复，更新所维护的会话状态，并确定交互行为与输出。考虑一个会话 $σ$，其前端为 $m ∈ \{audio, omni\}$；令 $k$ 表示以秒为单位的片段索引（此处省略会话上标）。媒体输入分别为 $x^{audio}_k = u_k$ 和 $x^{omni}_k = (u_k, v_k)$，其中 $u_k$ 包含因果音频特征，$v_k$ 包含对齐的视觉特征；若无可用帧，则 $v_k = ∅$。

令 $s_k$ 表示在第 $k$ 个数据块之前保留的前端状态，包括模型上下文、部分输出跨度以及之前已接收但尚未发送的回复文本。背景输入 $b_k$ 包含在该数据块中助手生成之前新接收的私有回复文本。之前接收到的回复仍然可以通过保留状态访问，因此它们的发送不需要在每个数据块中都生成新的背景消息。运行时反馈 $η_k$ 记录因果事件，例如播放确认。输出 $O_k = (c_k, Y_k, D_k, S_k)$ 包含交互控制标记、前景文本、委托文本和语音 token；只有 $Y_k$ 和 $S_k$ 是面向用户的。因果运行时转换是：

```math
(s_{k+1},O_k)=F_m(s_k,x^m_k,b_k;η_k).\tag{1}
```

其中，$F_m$ 负责汇总流式解码与运行时调度，同时确保各数据块（chunk）内部维持因果性的输入输出顺序（详见第 4.3 节）。委托文本 $D_k$ 可能跨越多个数据块。当请求完成时，系统会提交一项工作任务；该任务的“证据边界”（evidence boundary）在请求开始时即已确定，而其准备好的回复则可在后续的输入边界处被纳入处理流程。对于委托回复，前端会利用当前的交互状态，对由执行框架（harness）准备好的文本进行语音输出调度。第 5 节详细阐述了任务捕获、能力执行及回复交付的过程。

## 4.Model Design

Realtime-Venus-Omni 和 Realtime-Venus-Audio 分别是 Realtime-Venus 的全模态（omni-modal）和纯音频（audio-only）流式前端。这两个前端均在单一的自回归交互循环中，持续处理输入信号，判断是否以及何时做出响应，并生成语音。我们基于开源的 9B 参数模型 MiniCPM-o 4.5 开发了这两个前端。它们均引入了一种“流内委派协议”（in-stream delegation protocol），将对延迟敏感的前端交互循环与第 5 节所述的“委派框架”（Delegate Harness）相连接；这使得复杂请求能够在感知和语音生成持续进行的同时，以异步方式执行。此外，**Realtime-Venus-Omni 还集成了一个无需额外训练的长视频记忆模块，能够在长达数小时的交互会话中保留相关的视觉上下文信息**。

/>

该模型系列沿用了 MiniCPM-o 4.5 的 Omni-Flow 架构，如图 5 所示。Realtime-Venus-Omni 利用 SigLIP2 和 Whisper-Medium 对经过对齐的视觉与音频流进行编码；而 Realtime-Venus-Audio 则移除了基于 ViT 的视觉分支，仅处理流式音频。经投影处理后的特征由 Qwen3-8B 语言主干模型接收，该模型所生成的文本及隐状态为离散 S3 语音 Token 的预测提供条件。随后，一个流式“流匹配”（flow-matching）解码器将这些 Token 转换为波形。

流式处理被划分为以一秒为单位的片段。每个 Realtime-Venus-Omni 单元将当前帧的视觉 token 与在时间上对齐的音频特征交织在一起，而每个 Realtime-Venus-Audio 单元则仅包含音频特征。在每个单元中，语言模型会预测输出 **<|listen|>** 或 **<|speak|>**。对于发言单元，系统会生成响应文本，并以此为条件引导生成对齐的 S3 语音标记（speech tokens）。token **<|chunk_eos|>** 用于结束一个语音片段（chunk），而 **<|turn_eos|>** 则标志着助手一轮对话的结束。这种基于片段的调度机制使得感知过程能够与发言过程同步进行，且尚未表达出的后续内容仍可进行调整。这支持了两种交互能力：Realtime-Venus-Omni 能够实现“全方位主动式”响应——即持续进行观察与监听，并在出现新事件需要回应时主动发起发言；同时，两种模型均支持全双工对话，能够区分“应答性反馈”（backchannels，如“嗯”、“哦”等）与“打断”行为，从而适时停止、修正或重定向尚未表达出的后续内容。这些能力是通过第 4.5 节中介绍的主动式交互及全双工对话数据进行监督训练的。

### 4.2 Training-Free Long-Video Memory

流式音视频输入持续增长，而基础模型仅能维持一个有限的滑动上下文窗口。当会话时长达到数十分钟甚至数小时时，较早的内容会逐渐超出该窗口范围，导致后续查询无法获取之前的历史信息。因此，我们在流式处理流程中引入了一个外部长期记忆模块。该模块无需额外的训练或参数更新，且与经过微调的对话策略保持解耦。

**Memory construction**。若存储每一采样帧的视觉表征，内存占用及后续检索开销将随时间推移不断增长。受 AdaCodec 预测式视觉编码准则的启发，我们引入了一种基于“运动补偿预测代价”的视觉记忆门控机制。该机制通过轻量级的块级运动匹配，将当前采样帧与前一采样帧进行比对，并利用所得的预测残差与运动代价来评估两者间的视觉变化。为降低丢弃短时视觉事件的风险，我们进一步引入了“局部变化保护”机制及“最大连续丢弃”约束。该门控机制仅决定采样帧是否被归档至长期记忆中，不会影响其在短期上下文内的正常处理流程。被保留的帧将连同其视觉表征及时间戳一并存储；音频则独立保存，并与视频时间轴进行对齐。

**Memory retrieval**。受 MaxSim 算子的启发，该模块在查询 token 与各存储历史帧的视觉 token 之间执行细粒度匹配。对于每个查询 token，我们将其在某一帧内与各视觉 token 之间的最大余弦相似度，作为该 token 的匹配得分。为了突出那些在不同历史帧间匹配得分波动较大的查询 token，我们计算了这些得分的中位数绝对偏差（MAD），并将所得数值归一化为 token 权重。随后，将加权后的 token 级得分进行聚合，从而得出每一帧的语义相关性得分。基于这些语义相关性得分，我们首先筛选出一组候选帧，并按相关性进行排序。对于每个候选帧，我们将其与排名更靠前的候选帧进行比较，以评估其视觉新颖性。借鉴“最大边际相关性”（MMR）中的“相关性-多样性”原则，我们将语义相关性和视觉新颖性结合，计算出最终的检索得分。这些得分基于初始的相关性排序进行一次性计算，并在筛选过程中保持不变。最终，选取得分最高的候选帧作为历史证据，旨在保留与查询相关的信息，同时减少冗余的视觉内容。

**Context reassembly**。对于检索到的每一帧，该模块会获取其在时间上相邻的音频片段，并将重叠的时间区间进行合并。随后，将所选的历史帧及其关联音频，与近期的短时视听窗口以及当前的查询请求按时间顺序排列组合，共同构成用于生成答案的上下文。通过这种方式，模型能够在无需持续保留完整输入历史的前提下，找回超出其滚动上下文窗口范围的相关历史信息。

### 4.3 Unified stream serialization

Realtime-Venus-Omni 和 Realtime-Venus-Audio 将流式交互呈现为一系列时长为一秒的数据块（chunk）；若设时间边界为 $t_k = k$ 秒，则第 $k$ 个数据块涵盖的时间区间为 $[t_{k-1}, t_k)$。如图 6 所示，每个数据块都在统一的对话时钟下，将用户流、助手流和背景流这三条逻辑流对齐。

**User stream**。用户数据流是一系列按时间对齐、具有因果关联的感知特征。在 RealtimeVenus-Omni 中，来自 ViT 的投影特征与来自 Whisper 的投影特征交错排列，其中音频特征的频率约为每秒 10 个；而 Realtime-Venus-Audio 则省略了视觉特征。在助手输出期间，该数据流始终保持活跃，从而在统一的时间轴上完整保留了视觉事件、停顿、反馈以及重叠语音等信息。

**Assistant stream**。助手流（assistant stream）整合了前台文本、以每秒约 25 个 token 的速率生成的对齐式 S3 语音 token，以及可选的“纯文本”委派指令。在语音生成过程中，大语言模型（LLM）的隐状态保留了上下文中的韵律信息；而委派指令则会被发送至后端，不会被转化为语音输出。

**Background stream**。后台数据流是一个异步的纯文本序列，它将交互模型与功能更强大的后端智能体连接起来，以执行复杂的推理任务及基于工具的任务。委派指令会触发后端计算，这会导致响应出现时长不定的延迟。

挂起的任务不会产生任何结果词元（Result Tokens），因此前台交互可以继续进行。一旦任务结果满足返回条件，其结果便会在某个可用的分块边界（Chunk Boundary）处，作为外部上下文插入到助手输出流之前，而不是作为预测目标。

这三个流被交错合并为一个统一的词元流，由大语言模型（LLM）主干网络进行处理。其序列化格式如下：

```text
chunk 5:  <unit> V A → <listen> </unit>
chunk 6:  <unit> V A → <speak> T <chunk_eos><turn_eos> </unit>
chunk 7:  <unit> V A → <speak> <delegate> T </delegate><chunk_eos><turn_eos> </unit>
chunk 8:  <unit> V A → <listen> </unit>
...
chunk 13: <unit> V A → <listen> </unit>
chunk 14: <unit> V A <backend> T </backend> → <speak> T <chunk_eos><turn_eos> </unit>
```

*注（Notes）。* 每一行代表一个单元（Unit），其格式为 `<unit> input → output </unit>`。为清晰起见，图中将输出展示在单个分块内；但在实际应用中，单轮对话的文本输出词元（$T$）可能跨越多个连续的分块。

这里，$T$ 表示文本词元，$A$ 表示音频表示，$V$ 表示经过投影的视觉表示。在 Realtime-Venus-Omni 中，$V$ 和 $A$ 词元根据各自的到达时间交错排列，而 Realtime-Venus-Audio 仅对 $A$ 进行序列化。

外部工具请求以委托片段（Delegate Spans）的形式出现，而工具返回的结果则以后台片段（Background Spans）的形式出现在共享时间线上。我们向分词器（Tokenizer）、输入嵌入（Input Embeddings）和语言模型输出头（LM Head）中添加了四个控制词元：`<delegate>`、`</delegate>`、`<backend>` 和 `</backend>`。当需要调用工具时，模型会在委托片段中生成一个自包含的自然语言任务，该任务不会被显示或语音播报。后台智能体（Backend Agent）将该任务分解为一个或多个函数调用，并在某个可用的输入边界处，通过后台片段返回符合条件的结果。因此，即使助手正在进行语音输出，新到达的请求也可以在不结束前台对话轮次的情况下被分发执行，而复合请求则可以按照语义顺序触发多次调用。在这两种情况下，工具执行都与前台语音生成和感知过程异步并行进行。

三个状态词元用于表示全双工（Full-Duplex）对话轮次控制。`<listen>` 表示在不进行语音输出的情况下持续感知，`<speak>` 标记前台生成处于活跃状态，而 `<turn_eos>` 则表示一个完整的助手对话轮次结束。这些词元共同提供了一个紧凑的分块级接口，用于解释后台通道（Backchannels）、区分打断（Interruptions），以及协调监听与说话状态之间的切换。

为了使生成的语音与对话时钟同步，我们根据累积的播放进度调整文本输出。令 $\tau_{k-1}$ 表示此前已调度语音的结束时间，$\mathcal{D}(Y_{k,1:n})$ 表示前 $n$ 个候选文本词元的预计持续时间。在第 $k$ 个分块处，我们选择：

```math
n_k = \arg\min_n \left| \tau_{k-1} + \mathcal{D}(Y_{k,1:n}) - t_k \right|,
\tag{2}
```

其中，$t_k$ 表示当前分块边界的时间，$\tau_{k-1}$ 则记录累积的播放进度。当语音播放进度滞后时，调度器会输出更少的文本词元；而当存在更多可用的播放容量时，则会输出更多文本词元，从而使响应与最新的用户音频和后台结果保持同步。在训练过程中，文本词元及其对应的 S3 词元根据各自的起始时间被分配到不同的分块中，使模型能够学习依赖历史上下文的交错排列方式，而不需要固定的文本与语音比例。

### 4.4 Full-duplex interaction

我们将语音交互建模为在三个同步数据流上进行的分块级自回归建模（Chunk-level Autoregressive Modeling）。令 $U = (u_1, \ldots, u_K)$ 表示因果用户音频特征，$B = (b_1, \ldots, b_K)$ 表示每个分块处可用的稀疏后台结果，$O_k = (c_k, Y_k, D_k, S_k)$ 表示第 $k$ 个分块处的助手输出。其中，$c_k$ 是交互控制词元（Interaction-control Token），$Y_k$ 是前台响应文本，$D_k$ 是可选的委托请求（Delegate Request），$S_k$ 是与之对齐的 S3 语音词元片段。对于某个分块中未激活的字段，使用空序列表示。

参数为 $\theta$ 的大语言模型（LLM）负责预测交互控制、前台文本和委托文本，而参数为 $\phi$ 的语音解码器（Speech Decoder）则根据 LLM 的隐藏状态 $H$ 生成语音词元。联合策略（Joint Policy）可以分解为：

```math
p_{\theta,\phi}(O_{1:K} \mid U,B)=
\prod_{k=1}^{K}
p_{\theta}(c_k,Y_k,D_k \mid U_{\leq k},B_{\leq k},O_{<k})
p_{\phi}(S_k \mid H_{\leq k},Y_{\leq k},S_{<k}).
\tag{3}
```

这种分解方式将声学生成（Acoustic Generation）置于主 LLM 之外，同时允许语音、轮次控制和任务委托共享相同的语义表示。后台结果属于外部观测（External Observations），而非模型输出，并且只有在相应的后台计算完成后才会变为可用。

控制变量 $c_k$ 决定助手是继续监听、进行语音输出，还是结束当前对话轮次。由于 $c_k$ 是根据与响应生成相同的语义表示预测得到的，因此，系统会根据重叠音频在对话中的作用来理解它，而不是将其统一视为停止信号。我们区分以下几种情况：

- **停顿与背景噪声（Pauses and Background Noise）。** 静音、犹豫或并非针对助手的声学活动会产生 `<listen>`，使感知过程保持持续活跃，而不会过早开始或终止响应。

- **附和反馈（Backchannels）。** 类似于“yes”或“right”的简短回应并不意味着用户要取得对话中的话语权。模型会保持 `<speak>` 状态，并继续执行当前的响应计划。

- **打断（Interruptions）。** 当用户通过纠正、改变话题方向或提出新请求等重叠语音取得对话主导权时，模型会输出 `<turn_eos>`，以终止已经过时的响应。随后，模型会在生成下一个 `<speak>` 片段或委托请求之前，将新的用户意图整合到对话状态中，并根据新输入修改尚未说出的后续内容，同时保持已经播放的音频不变。

我们将打断建模为事件条件驱动的语义控制（Event-conditioned Semantic Control），并对状态转换及其后续生成轨迹进行联合监督。**停止/拒绝（stop/reject）** 操作会结束当前轮次并丢弃尚未说出的剩余内容；**修复/更新（repair/update）** 操作会整合新的信息，并重新生成已经过时的后续内容；而 **重定向/后续请求（redirect/follow-up）** 操作则会暂停当前计划，并将控制权转移到新的请求。通过在轮次控制、文本生成、语音生成和委托任务生成之间共享语义状态，系统能够针对声学特征相似的重叠语音产生不同的后续响应，从而实现超越语音活动检测（Voice Activity Detection，VAD）所触发的二元反应的原生全双工控制（Native Full-Duplex Control）。
